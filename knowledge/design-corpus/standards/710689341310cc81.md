# Contract 05 — Production Operations Contract

## Objective

Operate creative production as a reliable, reversible pipeline with evidence for each release.

## Operating model

```yaml
production_run:
  run_id: string
  brief_ref: string
  owner: string
  risk_tier: low|medium|high
  stages:
    - intake
    - policy_check
    - generate_or_build
    - validate
    - approve
    - release
  artifacts: [{path: string, sha256: string, role: source|intermediate|release}]
  environment: {tool_versions: [string], dependency_lock_hash: string|null}
  rollback: {trigger: string, owner: string, procedure_ref: string}
```

## Reliability controls

- Assign a single accountable owner and review owner for every release packet.
- Define acceptance checks before production: format, copy, claims, rights, accessibility, functional behavior, and delivery channel.
- Use immutable hashes for inputs, approved policy, prompts, references, and released artifacts.
- Set retry limits at three attempts per failed operation. Escalate failures that need changed inputs, new authority, or a non-retryable action.
- Keep an artifact index linking release outputs to source assets, run records, approvals, and validation evidence.
- Define rollback as a concrete removal, reversion, or replacement procedure with owner and maximum response target.

## Creative system operations

Treat a campaign’s Aesthetic Field as a versioned production dependency. The run record captures the signature tension, material logic, distinctive moves, prompt version, reference abstractions, and evaluator scores for signature integrity and derivation distance.

Use bounded exploration: define the number of concept routes, generate evidence for each route, select one route against the rubric, then develop it. This produces deliberate novelty while preserving cost, provenance, and reviewability.

| Stage | Required output | Gate |
|---|---|---|
| Field | Aesthetic Field and risk classification | Brand owner accepts intent |
| Routes | Three to five materially different concept routes | Rights and accessibility constraints attached |
| Selection | Scored comparison with rejected-route reasons | Owner selects one route |
| Systemization | Repeatable type, image, motion, and layout rules | Signature integrity passes |
| Production | Channel-specific assets and metadata | Standard release checks pass |

## Service levels

Set per workflow, rather than fabricating universal numbers:

```text
SLO: [e.g., approved asset delivery latency]
Error budget: [allowed failed or late runs per period]
RTO: [time to restore delivery capability]
RPO: [maximum acceptable lost production metadata]
Cost ceiling: [per run / campaign / period]
```

## Observability

Track run count, pass rate by gate, evaluation scores, rework cycles, validation failures by category, approval latency, delivery latency, asset provenance coverage, cost per accepted output, and rollback/takedown incidents. Track creative-health indicators separately: first-impression pass rate, signature-integrity score, derivation-distance escalations, accessibility-equivalence pass rate, and cross-channel coherence score. Avoid recording protected input data in logs.

## Release gate

| Check | Required result |
|---|---|
| Artifact integrity | Hashes match approved outputs. |
| Contract validation | Applicable contracts are complete and passing. |
| Approval | Required owners approve the exact release packet. |
| Delivery readiness | Channel format, metadata, URLs, accessibility materials, and tracking are verified. |
| Recovery | Rollback procedure and owner are recorded. |
| Creative integrity | Aesthetic Field, signature review, and reference-abstraction decision are recorded. |

Release only after the gate record is signed. Preserve the release packet and validation evidence for the policy-defined retention period.
